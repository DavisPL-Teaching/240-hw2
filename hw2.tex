\item
This problem will revisit the BF language from HW1.

One extremely important intermediate representation in the context of real compilers is that of a \emph{control flow graph}.
To define a control-flow graph for a language, we define a set of nodes and edges.
These are defined as follows:
\begin{itemize}
\item \textbf{Nodes:}
The nodes are the set of \textbf{basic blocks} of the program.
A basic block is a sequence of instructions, none of which is a branching or loop statement (with the possible exception of the very last statement).
In the context of BF, that means it will be a sequence of instructions in the program that doesn't have the \texttt{[]} characters, except (possibly) its very last character.
The idea of a ``basic block'' is that it is a basic sequence of instructions that can be executed in order -- and is always executed in order, ``as a whole'' -- with exactly one entry and exit point. In particular, it is impossible for any other part of the program to ever jump or branch to the middle of a basic block.

Also, one special basic block is designated as the entrypoint of the program, and one as the exit point.
The exit point block (unlike the others) may be empty, in the case that the program ends in a jump or branch statement (to distinguish from the block of instructions prior to the jump, and after the jump when the program will terminate).
The entry point block should always be nonempty, unless the program itself is empty, in which case it should have only one basic block, which is both the entry and exit point.

\item \textbf{Edges:}
The edges are then from one basic block to another, if it is possible for that basic block to transition to the other one after it finishes executing.
For example, in languages with \texttt{if} statements, for the basic block immediately prior to an \texttt{if} statement, it would have an edge to both branches of the \texttt{if}. In languages with \texttt{loop}s (of all kinds), the basic block immediately prior to the loop will have an edge to both the block inside the loop, and after the loop.
Often, these edges are labeled with \texttt{true} or \texttt{false} corresponding to the result of the prior test resulting in the branch.
\end{itemize}

For this problem, write two functions:
\begin{verbatim}
pub fn num_basic_blocks(bf_prog: &str) -> usize
\end{verbatim}

which takes a BF program as a plain ASCII string and calculates the number of basic blocks; and

\begin{verbatim}
pub fn num_edges(bf_prog: &str) -> usize
\end{verbatim}

which takes a BF program as a plain ASCII string and calculates the number of edges.
Both functions may assume the BF program is valid (has matching loop instructions)
It may be the empty string.

You do not need to actually write a compiler which takes the BF program and calculates its control flow graph as an intermediate representation as part of this problem, though you may choose to do so.
We will grade only your two functions for correctness.

You may want to write some unit tests for your functions to ensure they are working correctly.

Most programming languages that are designed and studied in practice are what is called \emph{Turing-complete}.
This can be defined as ``has the ability to simulate, and can be simulated by, a Turing machine'', or it may be defined more informally as simply ``has the ability to simulate, and can be simulated by, any regular program'' (such as one written in Python or C).
Alternatively, it may be defined in terms of concepts introduced in HW1, as:
the semantics of the language can both simulate BF, and can be simulated by BF.

However, not all languages are Turing-complete.
For example, from class, \texttt{RandProg} is not Turing-complete. It has only Boolean variables, so cannot store and access infinite memory. It would be Turing-complete if we were to add integer variables and loops (for example, \texttt{while} loops or \texttt{label/goto} statements).

In the following there are six parts:
Parts (a)-(b) will show that we can design a language that is \emph{weaker} than Turing-complete,
and parts (c)-(d), \emph{stronger} than Turing complete.
Parts (a) and (c) will ask for proofs, but parts (b) and (d) will only ask for your informal reasoning.
Part (e) is a free response question,
and part (f) is optional extra credit.

For all parts, we could use BF is used as a stand-in language for a Turing-complete language. However, we will instead work with the following less-contrived language, called WHILE, which is closer to real programs.
It has the following \textbf{Syntax} and \textbf{Semantics}:

\begin{itemize}
\item \textbf{Syntax:}
\begin{verbatim}
    Var ::= x | y | z
    IntExpr ::= 0 | 1 | Var
                | (IntExpr + IntExpr) | (IntExpr * IntExpr)
    BoolExpr ::= IntExpr < IntExpr | IntExpr == IntExpr
    Prog ::= Var := IntExpr
             | Prog ; Prog
             | If { BoolExpr } Then { Prog } Else { Prog }
             | While { BoolExpr } Do { Prog }
\end{verbatim}

\item \textbf{Semantics:}
For the semantics, assume that we are given a deterministic reference interpreter for \texttt{WHILE} whose behavior is as you expect (for example, matching how while loops would be executed in Python or C), and that its output is taken as the definition. This is similar to how we saw in HW1 that \texttt{BF} semantics could be defined using a reference interpreter, for the non-extra-credit version.

For the reference interpreter, assume that it takes the initial values of \texttt{x}, \texttt{y}, and \texttt{z} as input, and the final values of \texttt{x}, \texttt{y}, and \texttt{z} are output.  Then, assume that
$((x_0, y_0, z_0), \texttt{prog}, (x_1, y_1, z_1))$ is valid if, when running the program \texttt{prog} as you would expect (for example, interpreting If statements and While loops as they are usually understood), starting with initial values of the variables $(x_0, y_0, z_0)$, $(x_1, y_1, z_1)$ are the final values of the variables.
The expression \texttt{While \{ BoolExpr \} Do \{ Prog \}}
means that we check whether \texttt{BoolExpr} is true, and each time that it is true, we execute the loop body.

Finally, there is one important edge case -- what is the semantics when the WHILE program does not terminate?
Assume in this case that the output is $(-1, -1, -1)$.\footnote{
    You might think that the output should be empty -- i.e., the empty set of possible outputs -- in this case. But this is undesirable! Recall that making the semantics the empty set
    (even on some particular input) leads to there being no possible valid interpreter for the language. See poll on Oct 28.
}
\end{itemize}

Consider the following language, similar to \texttt{WHILE}, called \texttt{FORLOOP}:

\begin{itemize}
\item
\textbf{Syntax:}
\begin{verbatim}
    Var ::= x | y | z
    IntExpr ::= 0 | 1 | Var
                | (IntExpr + IntExpr) | (IntExpr * IntExpr)
    BoolExpr ::= IntExpr < IntExpr | IntExpr == IntExpr
    Prog ::= Var := IntExpr
             | Prog ; Prog
             | If BoolExpr Then { Prog } Else { Prog }
             | For { Var } From { IntExpr } To { IntExpr } Do { Prog }
\end{verbatim}

\item
\textbf{Semantics:}
The semantics is the same as for \texttt{WHILE},
except for \texttt{For} loops:
in that case, the expression \texttt{For \{ Var \} From \{ IntExpr \} To \{ IntExpr \} Do \{ Prog \}} means that the starting integer $i$ and ending integer $j$ will be calculated up front, and then the for loop will be executed by setting \texttt{Var} to every value $i, i + 1, i + 2, \ldots, j - 1$ (like a Python \texttt{range}).
This remains the case even if the variable \texttt{Var} is modified in the loop body. So, modifications to \texttt{Var} in the loop body are only retained for the duration of that loop body, and don't affect the following loop iteration.
If $j \le i$ immediately before the start of an iteration, the for loop will terminate immediately.
\end{itemize}

\section*{\normalsize Appendix: Helpful note on reducing boilerplate for \texttt{RandProg}:}
In class, we saw that creating \texttt{RandProg} programs via our Rust enum directly produces a lot of \texttt{Box::new(...)} and \texttt{.clone()} syntax.
This is neither necessary nor desirable!
Here is a helpful hint about how to avoid that. You can create an impl block like this, and give it various shortcut methods for creating various \texttt{RandProg} programs. For example:
\begin{verbatim}
impl RandProgP2 {
    pub fn seq(prog1: &RandProgP2, prog2: &RandProgP2) -> RandProgP2 {
        RandProgP2::Seq(
            Box::new(prog1.clone()),
            Box::new(prog2.clone())
        )
    }
    pub fn if_then(/* fill in */) -> { /* fill in */ }
    // etc., add other common logic or composition operations as needed.
}
\end{verbatim}

BTW, if you are wondering about the \texttt{.clone()}s - these are really not necessary, and they result in extra memory allocation. The ``correct'' way to write the code is to use the standard library's reference-counted pointer type, \texttt{Rc}\footnote{
    See \url{https://doc.rust-lang.org/std/rc/struct.Rc.html}.
}
in your language \texttt{enum} instead of plain \texttt{Box}.
Then, instead of using \texttt{Box::new()} your shortcut methods would look something like this:
\begin{verbatim}
impl RandProgP2 {
    pub fn seq(prog1: &Rc<RandProgP2>, prog2: &Rc<RandProgP2>) -> Rc<RandProgP2> {
        Rc::new(RandProgP2::Seq(
            Rc::clone(prog1),
            Rc::clone(prog2)
        ))
    }
}
\end{verbatim}

This uses \texttt{Rc::clone}, which is a shallow clone that only copies the reference-counted pointer.
Although not required, you are welcome to use this alternate design if you would like to.
(It should only affect your internal methods.)
